# Audit: manyfaced-honeypot — Architecture & Data Integrity

**Date:** 2026-06-09  
**Scope:** Full codebase audit covering architecture, data integrity, correctness, design, config/packaging/ops, and bundle cleanup.

---

## Critical — architecture & data integrity

### 1. The entire BotProfile subsystem is dead state
The entire BotProfile subsystem is dead state — collected, then discarded every request.  
This is the biggest architectural problem. HTTPHandlerBase has a full per-bot tracking system: BotProfile objects with escalation levels (IDLE→DEEP_EXPLOIT), request_history, detected_behaviors, capture_credentials(), full request/response dialogue, plus get_stats()/get_all_profiles()/clear_profile(). The bot_profile.py docstring calls the dialogue "the most valuable artifact." But Router.dispatch() does handler = route.handler_cls() on every single request (router.py:139), so each handler instance — and its bot_profiles dict — is born and garbage-collected within one request. No profile ever sees a second request. None of this state is ever serialized into BearStorage or sent to the server. Confirm by grep: get_full_report, detected_behaviors, escalation appear nowhere outside the handler classes and tests. Either the per-request instantiation is wrong, or the profile system should be deleted — but you can't have both. Decide what the honeypot is actually trying to capture, then make the lifetime match.

### 2. detected_id taxonomy has collapsed to two values
detected_id taxonomy has collapsed to two values, contradicting the data model. Every service handler hardcodes DETECTED_ID = 1; only GenericHandler differs (4294967294). So in the DB, every WordPress / phpMyAdmin / Jenkins / Tomcat / Drupal / cPanel / Bitrix / WebDAV hit is indistinguishable — all 1. The whole point of routing to service-specific handlers is lost at the storage layer. Meanwhile status.py defines a rich constant space (SSH_CLIENT, UNKNOWN_REDIS, UNKNOWN_TLS, EMPTY_CONNECTION…) that the HTTP handlers don't participate in. This is why TODO.md item #2 says "all detected_id = UNKNOWN_HTTP" — partly a detection bug, but also that the taxonomy was never given distinct per-service values.

### 3. Two complete, parallel client server-loop implementations
Two complete, parallel client server-loop implementations; one is entirely unused. client/server_factory.py (381 lines) implements create_server / create_multiport_server / _capture_credentials / _is_interactive_protocol — a more capable version of the same loop that lives in client/client.py. It is imported nowhere (grep confirms zero references outside the file itself). Worse, its _capture_credentials generalizes credential capture to all interactive protocols (TELNET/FTP/POP3/IMAP/VNC), which is exactly the feature the recent commits (#88–#91) were retrofitting into the other path. You have the better implementation sitting dead on disk while patching the inferior live one. Pick one.

### 4. Three independent copies of HTTP credential-extraction logic
Three independent copies of HTTP credential-extraction logic that have already drifted. The same username/password field lists and URL-decode table are duplicated in http_handler.py::_extract_http_credentials, base_handler.py::_extract_credentials, and again inside jenkins_handler.py / tomcat_handler.py / phpmyadmin_handler.py. They already disagree: http_handler returns a str ("user=…, pass=…"), base_handler returns a dict. The hand-rolled URL-decode (a list of .replace() calls) is itself fragile — it mishandles ordering (%25→% runs before other percent-codes, so %2520 decodes wrong) and silently differs from urllib.parse.unquote_plus. One decoder, one field registry, one return type.

## High — correctness & design

### 5. BaseHandler's "safe" processing path is structurally broken
BaseHandler's "safe" processing path is structurally broken and swallows errors to stdout. process_request_safe() calls _common_processing() (a no-op pass) instead of process_request(), so it does nothing useful, and on error it does print(f'Error…') rather than logging. It's never called in the live path, but it's public API on the server's base class and will mislead anyone who wires it up. Decide whether _common_processing is a real extension point or remove the safe-wrapper entirely.

### 6. Router.routes property lies about what it returns
Router.routes property lies about what it returns. The docstring says "Number of routes in the table" but it returns the list itself; callers then do len(_router.routes). Minor, but it's on the public routing API and the kind of thing that causes a confused refactor later.

### 7. No Content-Length on any honeypot response
No Content-Length on any honeypot response — a uniform fingerprint. Every handler builds responses with Connection: close and no Content-Length (confirmed: all 12 handler files lack it). Real Apache/nginx almost always send it. A scanner fingerprinting responses sees the same anomaly on every "service" you impersonate, which partially defeats the many-faced premise. This is a design decision in the response-builder layer, not a one-line fix — the bodies are assembled ad hoc per handler.

### 8. SSH/non-HTTP detection only triggers credential capture for SSH
SSH/non-HTTP detection in the live client only triggers credential capture for SSH- responses. In client.py, the post-response capture branch is gated on output_data.startswith(b'SSH-'). The non-HTTP handler returns banners for FTP/SMTP/POP3/IMAP/Telnet/VNC too (and builds a BearStorage expecting later enrichment), but those never get the keep-alive credential-capture treatment in this path — only server_factory.py (the dead one) handles them. So the recently-added interactive-protocol capture is effectively inert in production. Ties directly to #3.

## Medium — config, packaging, ops

### 9. Config resolution logic exists in two places
Config resolution logic exists in two places. common/config.py has a private _resolve(); common/config_resolver.py has a public resolve_setting() that is byte-for-byte the same algorithm. config.py uses its own private copy and ignores the resolver module entirely (grep: resolve_setting is imported nowhere). One of them is dead.

### 10. Config schema is internally inconsistent
Config schema is internally inconsistent across the three files that define it. The dataclass reads sections [logging] file, [dump] dump_file, [lockfile] lockfile, and [security] default_key; but settings.toml.example omits dump/lockfile/default_key and ships backends = [...] (an array the resolver can't round-trip from a string); .env.example uses HONEY_PORT/HIVE_PORT/HONEY_HIVELOGIN while code expects HONEY_HONEYPORT/HONEY_HIVEPORT; and mfh.py writes a different generated file than Config.generate_config_file() produces. A user following any one document gets a config the others reject. Also: DEFAULT_KEY is validated as mandatory at import (config.py bottom) but used by nothing — startup can CRITICAL-log about a key that has no consumers.

### 11. Generated-config / --generate-config paths diverge
Generated-config / --generate-config paths diverge and one is dead-ish. mfh.run() auto-copies settings.toml.example to XDG on startup and there's a separate --generate-config flag and Config.generate_config_file() — three mechanisms producing two different file formats. Consolidate to one.

### 12. The CLI --proxy flag is defined but never read
The CLI --proxy flag is defined but never read. arguments.py adds -p/--proxy ("put honeypot behind proxy") and nothing consumes it; there's no X-Forwarded-For handling anywhere, so behind a proxy every bot logs as the proxy IP. Either implement real-IP extraction (and gate it on this flag) or drop the flag.

### 13. CI deploys master without running tests
CI deploys master without running tests. deploy.yml: the test job is if: pull_request || workflow_dispatch, and push-to-master goes lint→deploy, skipping tests ("fast-path"). The 76% coverage gate and 3.12/3.13/3.14 matrix only protect PRs; a direct push to master ships untested. For a service that parses hostile input, that's the wrong tradeoff.

### 14. Ruff formatter is disabled on 3 files
Ruff formatter is disabled on 3 files to dodge a bug, and that exclusion is silently load-bearing. pyproject.toml excludes db/storage.py, mfh.py, bearstorage.py from formatting due to a ruff 0.15.x except (A, B) bug. The lint workflow pins ruff==0.15.13 (the buggy line), but .pre-commit-config.yaml uses rev: v0.15.0 and the lint job earlier installs via .[dev] — version skew between pre-commit, the dev extra, and CI means "passes locally" and "passes CI" can disagree. Pin one ruff version everywhere and re-evaluate whether the exclusion is still needed.

## Low — bundle into one cleanup pass

These are small; grouping per your instruction:

- **Dead imports / re-exports:** AESCipher imported in client.py but unused (encryption is in report_sender.py); WebDAVHandler exported and imported but not in the route table (routes __init__ docstring even says it's excluded) — so WebDAV responses are unreachable in production despite 238+195 lines of handler+responses.
- **Magic-number checks:** bearstorage.py does if self.isDetected != 4294967295 - 3 (i.e. != SSH_CLIENT) with an inline arithmetic literal instead of importing the named constant.
- **Duplicated _INTERNAL_IPS frozenset** defined identically in both client.py and the dead server_factory.py; mid-file import threading / import struct scattered inside functions.
- **Typos in user-facing strings:** BearStorage.__str__ emits "datected:" and "hostname:" actually carries HIVELOGIN; arguments.py epilog says "sneaky chinese bot" (the module docstring above it says just "sneaky bot") — worth scrubbing for tone.
- **logger = logging.getLogger(__name__) defined twice** back-to-back at the top of mfh.py.
- **__del__-based connection closing on both storage backends** is unreliable (GC timing); fine given the context-manager support exists, but the __del__ is a latent footgun.
